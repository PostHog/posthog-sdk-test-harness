Add the opt-in `feature_flags_unsupported_filter_types` suite for adapters that declare both `feature_flags_local_evaluation_v1` and `feature_flags_unsupported_filter_types_v1`. It covers the sdk-specs rule that a property filter type other than `person`, `group`, `cohort` or `flag`, such as a cohort's `person_metadata` filter on `created_at`, is inconclusive locally. A `person_metadata` cohort leaf has no local value whatever `created_at` the caller passes, and the default getter (`allow_remote_fallback`, which this capability also requires) falls back to `/flags`. Leaf negation and an outer `not_in` don't turn it into a match. A `person` filter on `created_at` with the type set, omitted, `null` or `""` still matches locally. Another cohort leaf, a definitively false person filter or a later catch-all condition still decides locally, and an unknown type in one flag doesn't stop another flag from resolving. A case that also lists `created_at` as known absent runs only with `feature_flags_known_absent_v1`. Adapters that also declare `feature_flags_unresolved_reasons_v1` return the SDK's `unresolved_reason` for a local-only request with no value, and three more cases check that it is `unsupported_definition`. `get_feature_flag` gains the harness-only `expect_inconclusive` and `expected_unresolved_reason` step params, which are never sent to the adapter.
